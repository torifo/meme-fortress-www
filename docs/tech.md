## 🗄️ 超次元・心臓（データベース）

### フェーズ別DB戦略
データ量と要件に応じて段階移行する方針。過剰設計を避け、必要が出た時に切り替える。

| フェーズ | 状態 | DB | ストレージ | 公開先 |
| :--- | :--- | :--- | :--- | :--- |
| **フェーズ1** | 開発・初期公開 | **SQLite** | DB内 (TEXT/JSON) | ローカル / VPS |
| **フェーズ2** | 画像コンテンツ導入 | **SurrealDB** | オブジェクトストレージ (S3/R2/MinIO) | 自前サーバー |

---

### **フェーズ1: SQLite**（初期〜VPS公開）
> 🚨 **設計の大原則: 「DB移行を前提としたスキーマ・クエリ設計」を常に心がける。**
> SQLite に閉じた便利機能は使わず、SurrealDB（および他のDB）へ移植可能な形を保つ。

- **採用理由:** 数十万〜数百万件規模なら余裕。インフラゼロ・1ファイル運用・`scp` でデプロイ完了。
- **役割:** ミームマスター・投票ログ・ユーザー嗜好データの保存。
- **Rust連携:** `sqlx`（型安全クエリ）または `SeaORM`（マルチDB対応ORM）。
- **移行準備:**
  - ID は `TEXT` の UUID で統一（`AUTOINCREMENT` 不使用）
  - SQLite 固有機能（`WITHOUT ROWID`、独自関数、`PRAGMA` 依存ロジック）は避ける
  - `sqlite3 db.sqlite .dump > backup.sql` で全データ抽出可能な状態を維持
- **煽り:** 「軽量にして最強！ ファイル一発、即起動！ サーバー要らずで爆速展開！！」

---

### **フェーズ2: SurrealDB**（画像導入時に移行）
- **移行トリガー:** **画像コンテンツを扱い始めた時**
  - 理由: SQLite に BLOB を入れるとサイズ肥大・バックアップ困難・WAL ロック競合が顕在化
  - 画像導入時は DB だけでなくストレージ層の再設計が必要 → 自然な移行ポイント
- **特性:** Rust製・マルチモデル（Relational, Document, Graph, Real-time）
- **役割:**
  - カードの所有権、銀はがしの同期、ミームの相関図（グラフ構造）の管理
  - リアルタイム多人数セッション（ライブランキング、共有スワイプ）
- **画像配信:** **S3 / Cloudflare R2 / MinIO** などオブジェクトストレージと併用。DB にはメタデータ＋URLのみ。
- **サブ・オプション（バックアップ巨神）:** **DynamoDB** (AWS)
- **煽り:** 「書き込み爆速（ドォォォォン）！ 誰かが削れば世界が変わる！ ライブクエリで全ユーザーをリアルタイム接続だ！！」

---

### 移行を見据えた設計ルール
1. ORM レイヤーを噛ませてクエリ書き換えコストを最小化
2. スキーマは正規化＋UUID 主キー
3. CI に `.dump` をスケジュール、いつでも全データを別形式に変換可能な状態に
4. 移行は段階的に: スキーマ移行 → データ移行 → クエリ層差し替え → 旧DB凍結
